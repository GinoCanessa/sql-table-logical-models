Implementation and design notebook

SQL tables.
Logical identities.

Describe each table or view with a flat logical model. Bind its canonical URL to a local relation. Compose it with SQLView and SQLQuery Libraries using ordinary SQL joins.

Run the synthetic example
Keep both truths

The logical model helps tools discover columns and relationships. The declared SQL type and original DDL remain authoritative storage metadata.

Exploration snapshot: 17 November 2026
External relations are still a proposal.

Issue 426 explicitly excludes them from SQL on FHIR 3.0.0. This repository implements a local experiment, not an adopted Relation profile or a complete FHIR server. All new relation metadata uses a project namespace, never an invented HL7 canonical. [1]

Start without private data

Run it locally

Requires Node.js 24.10 or later and npm. Node supplies SQLite and HTTP; there are no runtime npm dependencies. Commands below use PowerShell.

Synthetic clinic

npm ci
npm run demo
npm start -- --database .\.data\demo.sqlite

The demo creates two patients, three visits, a native SQLite view and three stored artifacts. It refuses to overwrite an existing demo database. The server binds to 127.0.0.1:3000. Open the interactive playground to explore it; this documentation remains available at http://127.0.0.1:3000/docs/. Substitute your configured port when different.

curl.exe 'http://127.0.0.1:3000/$sql-run?subjectReference=Library/patient-visits&_format=json'

curl.exe -X POST 'http://127.0.0.1:3000/$sql-run' `
  -H 'Content-Type: application/fhir+json' `
  --data-binary '@examples\run.json'

The POST binds minimum_cost = 25 and returns only visit 10, with cost 40.5. The query follows a ViewDefinition projection, an active-patient SQLView and the physical visit table. All records are synthetic.

Describe the supplied database

npm run derive -- --database .\temp\fhir-comparison.sqlite `
  --base https://example.org/comparison `
  --out .\.data\comparison-models.json

npm start -- --database .\temp\fhir-comparison.sqlite `
  --base https://example.org/comparison `
  --artifacts .\.data\comparison-artifacts.sqlite

Derivation opens the source read-only and reads schema metadata, not records. Output includes the local abstract base plus one model per table/view. --out creates a new file only; omit it to write JSON to stdout through the compiled CLI. Keep canonical bases consistent between derivation and serving. Use a separate artifact store per source database.

The artifact store is SQLite, not the derived JSON Bundle. Pass a new .sqlite filename to --artifacts; the server creates it and regenerates source logical models directly from --database.

temp/, .data/, dependencies and build output are gitignored. Neither the supplied SQLite file nor its generated schema is needed to run the synthetic example. Generated metadata may itself be sensitive; do not commit a private schema accidentally.

From discovery to execution

Interactive playground

The running server serves a browser workbench at /playground/. It uses the existing JSON API and requires no frontend framework or separate development server. The root and /metadata remain CapabilityStatement endpoints.

Browse tables and artifacts

Choose tables/views, logical models, Libraries or ViewDefinitions in the left catalog, then filter by name or canonical. Table selection shows schema, key/index metadata, DDL and the generated model identity without reading rows. Load rows explicitly for bounded pages of at most 100 rows, further limited by the server execution ceiling. Primary keys define preview order; relations without a declared primary key have unspecified order. A full page enables Next even when the following page may be empty. This is a playground preview, not FHIR search pagination.

Generated models are read-only. Stored artifacts can be inspected, downloaded and edited as JSON. Libraries can be loaded into the SQL workspace or selected as operation subjects. Refresh catalog reflects saved artifacts; schema changes require a server restart.

Write SQL and generate FHIR Libraries

Start a query from a table or add it as a canonical dependency. The dependency label is the name used in SQL; labels are editable, and joins can combine multiple dependencies. Choose SQLQuery or SQLView, set the artifact ID and optional canonical/title/version, and enter SQL. Advanced controls accept Library parameter declarations and FHIR Parameters input values.

Generate Library produces JSON using the shared server helper, including matching base64 SQL and sql-text. It does not execute, save or fully validate SQL. Run SQL sends an inline Library through POST /$sql-run; results appear as a scrollable table and failures as OperationOutcomes. Save Library persists through the existing PUT endpoint and asks before replacing an existing ID. Saving a SQLView does not create a physical database view. Loading and editing a stored SQL Library preserves unrelated metadata and non-SQL attachments. Arbitrary SQL is represented as a Library, not automatically translated into a ViewDefinition or clinical FHIR resources.

Invoke FHIR operations

The console accepts the current SQL workspace, a stored reference, a canonical URL or an inline Library/ViewDefinition. Choose JSON, NDJSON or CSV, provide query inputs and optional inline context, then inspect the generated Parameters request. Send uses the form by default. To send a hand-edited Parameters resource, explicitly enable “Send edited JSON”; this also permits multi-subject exports.

The response includes HTTP status, raw output, row tables where applicable, decoded Binary payloads when requested, and OperationOutcome diagnostics. Export invokes $sql-export, follows its status/result flow, and exposes download links, manual status checks and cancellation/deletion. There is no continuous background polling; an export still pending after the initial check needs another status check. Existing backend restrictions still apply.

The server advertises its configured canonical base and row ceiling to the UI, so a custom base such as https://ginoc.io/fhir-comparison is used when generating new Libraries. Workspace SQL and form inputs live in browser memory until explicitly saved or downloaded; they are not automatically persisted across page reloads.

Small, separable layers

A schema pipeline and a query pipeline

SQLite catalog + PRAGMAs→ SqlSchema→ Logical models + bindings

SqliteSchemaReader reads columns, declared types, default SQL expressions, key order, generated columns, indexes and DDL. createLogicalModels is a pure, deterministic conversion. It produces a collection Bundle and a separate in-memory canonical-to-table binding registry. Database paths never enter the models.

Parameters + subject→ Canonical dependency graph→ Scoped SQL CTEs→ Read-only SQLite

The catalog combines generated models with artifacts persisted in a separate SQLite store. Evaluation resolves dependencies by canonical URL, builds nested CTEs under their relatedArtifact.label names, and binds query values rather than interpolating them. No source views or tables are created. A read transaction gives all subjects in one export a consistent SQLite snapshot.

Code map: src/schema.ts reads metadata; models.ts generates models; store.ts manages artifacts; engine.ts compiles/evaluates; operations.ts handles wire inputs and formats; exports.ts persists jobs; playground.ts supplies bounded browser helpers; server.ts exposes HTTP; cli.ts supplies commands; ui/ holds the browser workbench.

import { readSqliteSchema, createLogicalModels } from "./dist/src/index.js";

const schema = readSqliteSchema(".data/demo.sqlite");
const { bundle, bindings } = createLogicalModels(schema, {
  baseUrl: "https://example.org/sql",
  version: "1.0.0"
});

Local experimental contract

One flat StructureDefinition per relation

R5-shaped logical models provide machine-readable structure without claiming that arbitrary SQL rows satisfy FHIR primitive value constraints.

Each model has kind = logical, derivation = specialization, type = url and draft/experimental status. Derive and serve default to --relation-base local; use sof for the draft SQL-on-FHIR Relation canonical. The differential contains a 0..* root plus ordered scalar leaves. Generation writes explicit IDs and cardinalities; the Relation reader also accepts id-less draft elements, omitted column cardinalities (0..1) and boolean primary-key membership without inventing key order.

{
  "resourceType": "StructureDefinition",
  "id": "patient",
  "url": "https://example.org/sql/StructureDefinition/patient",
  "name": "patient",
  "kind": "logical",
  "abstract": false,
  "type": "https://example.org/sql/StructureDefinition/patient",
  "baseDefinition":
    "https://example.org/sql-table-logical-models/StructureDefinition/Relation",
  "derivation": "specialization",
  "differential": {
    "element": [
      { "id": "patient", "path": "patient", "min": 0, "max": "*" },
      {
        "id": "patient.id", "path": "patient.id", "min": 1, "max": "1",
        "type": [{ "code": "integer64" }], "mustHaveValue": true,
        "mapping": [{ "identity": "sql", "language": "application/sql;dialect=sqlite", "map": "INTEGER" }]
      }
    ]
  }
}

This excerpt omits status, the primary-key position and DDL. Column order follows SQLite cid; composite key order is recorded separately. A view has relation-kind = view; SQLite may not supply declared types for every view column.

Names are logical; SQL names are lossless

Already-safe logical names are retained. Other names receive a deterministic sanitised name with a SHA-256 suffix; resource IDs use a separate FHIR-id-safe encoding. This distinguishes names such as a-b, a_b and a.b. Original physical names survive in sql-name; SQL identifiers are always quoted. These identities are name-derived, so renaming a table changes its generated canonical.

Nullability is not simply “primary key means required”

All columns have max = 1. min = 1 reflects declared NOT NULL or an actual SQLite non-null key guarantee: a rowid-alias INTEGER PRIMARY KEY, a WITHOUT ROWID primary key, or a STRICT primary key. An ordinary nullable TEXT/composite primary key remains min = 0. Inline INTEGER PRIMARY KEY DESC is not treated as a rowid alias. View nullability is only what SQLite reports. [6]

Metadata does not silently become validation

Guaranteed non-NULL leaves also set mustHaveValue=true; nullable leaves omit it. Insert defaults stay unevaluated SQL, never defaultValue[x]. Row CHECKs preserve the predicate on a root constraint. Only simple NULL tests translate to FHIRPath; other predicates stay SQL rather than guessing SQLite comparison or NULL semantics. Ordered primary/unique keys and foreign keys concern multiple rows and are not invariants. Original DDL and index metadata preserve generated expressions, collation, order and partial predicates. This is not full StructureDefinition or row validation.

Storage facts / authoring hints

SQLite type mapping

The exact declared type, SQLite affinity and FHIR-oriented hint are distinct pieces of metadata. Affinity is computed in SQLite's documented order. [6]

Schema-derived primitive hints (no sampling)
Declared name or affinityFHIR hintQualification
BOOL, BOOLEANbooleanExact well-known spellings; SQLite may still store non-boolean values.
DATE; TIMEdate; timeExact names; formats of stored values are not checked.
DATETIME, TIMESTAMP, optionally (precision)dateTimeTime zones and actual encodings are not inferred.
INTEGER affinity (contains INT)integer64Preserves the possibility of signed 64-bit SQLite values; not FHIR's 32-bit integer.
TEXT affinity (CHAR, CLOB, TEXT)stringNo JSON, code or canonical semantics guessed from names.
Explicit BLOBbase64BinaryAffinity may still differ if an earlier rule matches the declared type.
No declared typestring + warningSQLite affinity is BLOB. The hint is provisional, not a sampled type.
REAL (REAL, FLOA, DOUB); remaining NUMERICdecimalDeclared precision/scale stay in the selected SQL type encoding; SQLite does not enforce fixed decimal precision.

Affinity precedence matters: FLOATING POINT contains INT and therefore has INTEGER affinity. The mapped FHIR type is an authoring aid, not a replacement for the declared type grammar. The design starts from the FHIRPath Lab mapping but intentionally uses integer64 and keeps foreign-key values primitive. [5]

--integer-type integer64|integer|auto applies to derive and serve. The default is integer64. Explicit integer asserts a 32-bit range; auto recognizes a whole CHECK of the form x BETWEEN low AND high with integer literals within that range. SMALLINT or INT alone proves no bound. String columns declared CHAR, VARCHAR, NCHAR, NVARCHAR, CHARACTER, CHARACTER VARYING or VARYING CHARACTER with a representable length carry maxLength. SQLite does not enforce declared lengths; over-length strings are not truncated.

Wire values stay faithful to SQLite

Run and export now serialize modeled integer64 as an exact decimal string at every magnitude ("1", "9223372036854775807"), not sometimes a JSON number. Modeled integer and decimal remain finite JSON numbers, including integral decimal 40. An incompatible numeric value fails instead of silently overflowing. Direct columns and aliases use their prepared origin; a Library can type an expression with a matching named parameter[use=out]. Unresolved expressions keep storage-value conversion: a safe integer becomes a number, a larger one a string. BLOBs remain base64 and NULL remains null. JSON is an array; NDJSON is one row per line. CSV uses raw cells, optional headers, quoting and CRLF; NULL and the empty string are indistinguishable there.

Joins remain ordinary SQL

Keys describe relationships, not nested rows

Primary-key columns retain their ordered key position. Each foreign key is a relation-level composite extension with an ordered source/target column pairing, a target table, an optional target model canonical, and update/delete actions. An omitted REFERENCES column list is resolved against the target's ordered primary key when possible.

Foreign-key columns keep their storage-derived primitive type. They do not become Reference objects or nested relation instances. This keeps SQL joins lossless and supports composite and non-primary unique keys without inventing a reference-serialization convention. The gist discusses other FK spellings; issue 426 leaves foreign keys out of its initial standardisation scope. Our metadata is an independent experiment. [2] [1]

SELECT p.patient_id, p.patient_name, v.id AS visit_id, v.cost
FROM patients p
JOIN visits v ON v.patient_id = p.patient_id
WHERE (:minimum_cost IS NULL OR v.cost >= :minimum_cost)
ORDER BY v.id

Here patients is a SQLView label and visits is a logical-model dependency label, not a physical table name. The physical mapping stays local. A declared foreign key is descriptive metadata; the query author still writes the join condition. No relationship is inferred merely because a column ends in Id or Key.

Reuse the existing composition vocabulary

Library, SQLView and ViewDefinition

SQL Libraries use the specification's LibraryTypesCodes#sql-query or #sql-view coding. Generated SQL attachments declare contentType = application/sql;dialect=sqlite, from https://sql-on-fhir.org/ig/CodeSystem/SQLContentTypeCodes. Attachment.contentType remains a primitive code, not a Coding object. SQL text lives in base64 data, the standard sql-text extension, or both. If both are supplied they must match exactly. Remote SQL attachments are rejected. The exported sqlLibrary() helper writes both representations. [3] [9]

Execution and the SQL workspace prefer a matching application/sql;dialect=sqlite attachment over the default application/sql attachment, regardless of attachment order. The default remains readable for compatibility with existing artifacts. If neither is available, a Library containing only other SQL dialects is rejected rather than translated. Generating from the SQL workspace replaces all SQL variants with one SQLite attachment; non-SQL attachments and unrelated metadata are retained.

Generated SQL Libraries and concrete table/view logical models also carry the local resource-level sql-content-type extension below; demo ViewDefinitions using SQLite sources include it too. This exposes the dialect even for models with DDL but no SQL attachment. The abstract Relation base is dialect-neutral and is not annotated. Imported/stored resources are not automatically rewritten; re-save a Library through the SQL workspace to update its SQL annotation.

"extension": [{
  "url": "https://example.org/sql-table-logical-models/StructureDefinition/sql-content-type",
  "valueCoding": {
    "system": "https://sql-on-fhir.org/ig/CodeSystem/SQLContentTypeCodes",
    "code": "application/sql;dialect=sqlite"
  }
}]
"relatedArtifact": [
  {
    "type": "depends-on",
    "label": "patients",
    "resource": "https://example.org/sql/Library/active-patients"
  },
  {
    "type": "depends-on",
    "label": "visits",
    "resource": "https://example.org/sql/StructureDefinition/visit"
  }
]

A dependency may be a configured logical relation, a supported ViewDefinition, or a SQLView Library. A SQLQuery may be an execution subject but not another query's dependency. Labels must be simple SQL identifiers and unique case-insensitively within their Library. Nested scopes avoid collisions between unrelated dependencies using the same label. Cycles and dependency chains deeper than 32 are rejected.

A deliberately limited relational ViewDefinition

The fixture's patient-projection uses resource = patient, a local source extension containing the relation canonical, and flat select.column entries. Each path is a direct logical column name; the binding maps it back to its physical SQL identifier. Column type is descriptive only. This is a local extension to ViewDefinition source semantics, not general FHIR resource evaluation.

FHIRPath functions, nested paths, where, constants, collections, forEach, nested select and unions are rejected. Use a SQLView for filtering, calculated expressions or joins. The local JS reference implementation has a real FHIR ViewDefinition evaluator; this project does not copy or claim that engine's conformance. [4]

Resolution and query parameters

Canonical references may include |version. A matching inline context dependency outranks the stored artifact. Ambiguous unversioned references fail rather than choosing an arbitrary version. Context entries must have unique URLs and all must be used somewhere in the invocation's dependency graph. A missing canonical returns a 404 OperationOutcome. Generated models cannot be edited or deleted via HTTP.

Input values are nested FHIR Parameters matched by declared Library parameter name and value[x] field. Supported declarations are scalar input string, integer, integer64, decimal, boolean, date and dateTime. Only :name SQL placeholders are accepted; undeclared placeholders and undeclared/repeated supplied values fail. Required inputs have min = 1; omitted optional inputs bind as SQL NULL. Parameterised SQLView dependencies are not supported. Date strings are passed through to SQLite; callers remain responsible for their FHIR lexical form.

Output declarations are not placeholders and need no input values. A SQLView with only output declarations can still be a dependency.

$sql-run inputs

Supply exactly one subjectCanonical (valueCanonical), subjectReference (valueReference.reference) or subjectResource (resource). Local references are Library/id or ViewDefinition/id. Optional inputs are parameters, repeating context, _format, header and _limit. GET supports only the primitive/query-string forms. Unknown operation parameters are rejected, not silently ignored.

_format accepts json, ndjson or csv. Without it, a supported Accept media type selects the format; otherwise NDJSON is the default. Accept: application/fhir+json requests a base64 Binary envelope. Explicit _format wins. XML, Parquet and _format=fhir are not supported. CSV includes column headers even for zero rows unless header=false. [3]

_limit caps returned rows after SQL evaluation semantics, including joins, aggregation and ordering. Zero prepares the query and returns no rows. The default safety ceiling is 1,000 rows, configurable with --max-rows. Exceeding it without a smaller explicit limit returns an error, never a silently truncated result; a requested limit above the ceiling is rejected.

$sql-export lifecycle

Each completed file has one output.model canonical alongside its name and download URI. The job retains the model derived from that same SQLite evaluation, even after a Library or dependency changes or the server restarts. Deleting the job deletes its files and snapshots; legacy jobs without snapshots remain readable.

curl.exe -i -X POST 'http://127.0.0.1:3000/$sql-export' `
  -H 'Content-Type: application/fhir+json' `
  -H 'Prefer: respond-async' `
  --data-binary '@examples\export.json'

The input contains repeating subject parts, each with a naming form, optional name and optional nested query parameters. Format, header and context apply to the whole job. A subject name defaults to its artifact name, or a generated ID; names must be unique and filename-safe, otherwise supply an explicit one. Export output defaults to NDJSON independently of Accept and never accepts _limit.

The unified system-level SQLRun and SQLExport definitions describe different outputs. Run declares one Binary return whose binary-content-model points to the local abstract Relation. Export returns an empty 202 with Content-Location and Retry-After. Poll that URL: 202 means pending; 303 Location identifies the final result. Success returns Parameters with exportId, status, top-level location (the polling URI), _format, start/end times, clientTrackingId if supplied, and one output per subject with its name and download location. Neither URI is a Binary. All subjects execute in one read transaction. Jobs and bytes persist until deletion. Interrupted jobs fail after restart; cancellation cannot preempt synchronous SQL.

Describe and discover a result contract

GET /$sql-describe?subjectReference=Library/patient-visits returns an ordered Relation. POST accepts a subject and repeated inline context, not execution inputs. Only the SQLite dialect is supported. No rows are sampled, required inputs bound, tables created or artifacts saved. Use _format=sql for destination DDL; _format=operation returns the system-level $sql-run definition specialized to this result. Its one Binary return carries one concrete model for every flat format, not a new invocation endpoint. Playground Describe result and Operation profile use the same request.

Library output declarations (use=out) match aliases, never placeholders. Unasserted Library outputs are nullable even for required source IDs. Unknown expressions retain storage values and an untyped element with a diagnostic, not a fully typed contract. Direct ViewDefinition projections retain required values, length, and dialect tags. Collections wrap non-NULL values in singleton JSON arrays. Booleans serialize as JSON booleans but raw SQLite 1/0 in CSV; CSV preserves quoting, ordered headers and NULL-as-empty.

GET /$feature-query?param=result-model@Library/patient-visits or query operation-profile. POST Parameters supports a feature definition canonical and versioned subject scope. GET /FeatureDefinition/{id} describes the seven local features: result-model, operation-profile, output-format, binary-content-model, sql-dialect, integer64-json and describe. Retrieve discovered contracts at this server by type/id or ?url=, not by contacting a canonical host. Saved graphs reconstruct deterministically; inline profiles contain request-local models. See the repository examples describe.json and feature-query.json.

--relation-validation warn|error controls imported Relations (warn for this transition). Strict mode rejects invalid descendants on write and resolution without changing stored resources. Optional --verify-output checks actual run and export bytes, including order, cardinality and exact primitive representations. A length overrun warns; an invalid required cell fails. Diagnostic counts on successful downloads/runs use X-Relation-Issue-Count.

Error contract: malformed inputs return 400 (or 415 for content type), missing artifacts 404, ambiguous/conflicting canonicals 409, query/shape/row-budget failures 422 and incompatible Accept 406. An unmet Required-Features: param=integer64-json(string) requirement would return 501 before evaluation or job allocation. Errors carry an OperationOutcome. Unexpected failures are logged and return 500. Request bodies are limited to 1 MiB.

Observed metadata, not sampled records

What the supplied database contributes

The supplied temp/fhir-comparison.sqlite contains 36 application tables, 839 columns, no native views and no declared foreign keys. These counts come from SQLite catalog/PRAGMA metadata on 17 November 2026. Generation yields 36 relation models plus the local abstract Relation base. No row contents are embedded in this documentation.

FhirPackages and Structures provide a useful exploration surface. Both have an INTEGER primary-key column named Key; Structures also declares FhirPackageKey. Their names suggest a possible join, but the database declares no foreign key, so the generator correctly emits no relationship for it. Any such join remains an author-supplied assumption requiring domain confirmation.

The data file stays in gitignored temp/. Real derived models should stay under gitignored .data/ until deliberately reviewed. The checked-in clinic fixtures exercise foreign keys, views and joins independently, so the implementation remains reproducible without the starter data.

Deliberate choices, easy to revisit

Logical discoverability, SQL fidelity

Implemented choice

A local Relation base

Recognise a relation by an explicit experimental base. Keep this canonical independent of the still-unsettled HL7 proposal so migration can be deliberate rather than pretending consensus.

Implemented choice

SQL types as text, not codes

Store the full declared type and DDL, alongside FHIR hints. Issue comments question FHIR types and suggest a DDL Library instead; the retained DDL makes that alternative possible without re-inventing storage grammar. [1]

Implemented choice

Binding is configuration

The discovered database determines the physical bindings. An uploaded logical model or attachment cannot redirect the server to a file, URL or another database. No CSV/Parquet loader or remote canonical fetching is implemented.

Future alternative

A DDL or dataset Library

A separate Library could hold DDL, source location or dataset identity, while the logical model remains a schema projection. That is not generated or resolved yet, and no new Library type is claimed to be standard.

Explicit boundaries

An exploration server, not a deployment boundary

Trusted local use only. There is no authentication or authorisation. The CLI binds to loopback, rejects cross-origin requests, disables extension loading, opens the source read-only and uses SQLite's authorizer to reject writes, PRAGMAs and ATTACH. Those safeguards do not make SQL safe for untrusted users. A query may read any table in the configured source database; dependency declarations are not access-control rules.

Execution is synchronous and buffered. Row caps do not bound execution time, aggregate/join complexity, row byte size or export-store growth. Long SQL blocks all requests, including cancellation. Run only trusted SQL; a network-facing service needs authentication, a read allowlist, worker/process isolation, execution/time/memory budgets and output retention. Use one server process per artifact store. Do not configure the artifact store as the source database.

No FHIR data ingestion, terminology dependencies, patient/group/_since filters, arbitrary FHIRPath, relation-source downloads, SQL writes, materialisation policy, FHIR search pagination or Parquet is implemented. Unsupported operation parameters and unsupported projection features fail explicitly. A native database view is introspected but its result constraints cannot be proven from column metadata.

Extending to other databases

The reader interface and explicit schema types separate discovery from generation, but the current dialect and mapper are SQLite-only. A PostgreSQL or SQL Server adapter must widen the dialect model, supply its catalog reader, implement declared-type mapping, and add an execution backend with equivalent identifier quoting, bindings, read-only enforcement and snapshot semantics. Reuse the flat model and canonical/label contracts; do not feed a different dialect into the SQLite affinity mapper.

Open design questions

Resolve the upstream Relation-versus-DDL direction before publishing a profile. Decide how source bindings are deployed, how curated canonical identities survive schema renames, and whether key/constraint metadata should become proper Extension definitions. A FHIR instance adapter, verified primitive conversions and a full ViewDefinition engine are separate additions, not consequences of schema introspection alone.

Semantic database comments are not parsed from DDL in this iteration. DDL itself is retained. The FHIRPath Lab design includes a comment parser and row/reference conversion; those capabilities are related prior art, not implemented features here. [5]
